# AI Architecture: ForgeFlow AI

## 1. Provider-Agnostic Abstraction

The AI Engine is designed to prevent vendor lock-in and allow seamless switching between AI models (e.g., OpenAI GPT-4o, Anthropic Claude 3.5 Sonnet, Google Gemini, or local models via vLLM).

### 1.1 The `AIProvider` Interface
All interactions with LLMs go through a strict Python abstract base class:

```python
class AIProvider(ABC):
    @abstractmethod
    async def generate(self, prompt: str, system_prompt: str, **kwargs) -> str:
        pass

    @abstractmethod
    async def structured_generate(self, prompt: str, system_prompt: str, schema: Type[BaseModel], **kwargs) -> BaseModel:
        pass

    @abstractmethod
    async def health_check(self) -> bool:
        pass
```

## 2. The AI Migration Pipeline

The AI Engine does not operate in a single "one-shot" pass. It uses a chained, verifiable pipeline driven by the AIR (Application Intermediate Representation).

### Stage 1: Migration Planner
- **Input:** The complete AIR (JSON) generated by the deterministic parser.
- **Task:** Map web routes to Flutter screens, web components to Flutter widgets, and state management (e.g., Redux) to Flutter equivalents (e.g., Provider/Riverpod).
- **Output:** A structured `MigrationPlan` (JSON Schema) detailing the target Flutter architecture.

### Stage 2: Code Generator (Batched)
- **Input:** The `MigrationPlan` and specific chunks of the AIR.
- **Task:** Generate the actual Dart source code.
- **Constraint:** Code is generated in logical batches (e.g., Models first, then Services, then UI Screens) rather than attempting to generate the entire repository in one API call.

### Stage 3: Code Reviewer
- **Input:** The generated Dart code from Stage 2.
- **Task:** Perform an AI-driven static review specifically looking for Flutter anti-patterns, mobile UX issues (e.g., non-responsive layouts), and adherence to the migration plan.
- **Output:** A boolean pass/fail and a list of specific fix recommendations.

## 3. The Bounded Remediation Loop

If the Code Reviewer (AI), or the deterministic Validation Gates (e.g., `flutter analyze`, `flutter test`), fail, the system enters the Remediation Loop.

1. **Diagnosis:** The error output (e.g., Dart compiler error) and the faulty file are packaged into a remediation prompt.
2. **Fix Generation:** The AI Provider is asked to supply *only* the corrected file or the specific diff.
3. **Application:** The Backend applies the fix to the Sandbox workspace.
4. **Re-validation:** The validation gate is re-run.
5. **Termination:** If the gate passes, the loop exits successfully. If the `MAX_RETRIES` (default 3) is reached, the loop aborts and marks the job as `FAILED`.

## 4. Prompt Versioning and Tracking

- Every prompt template is stored as a versioned artifact (e.g., `planner_prompt_v1.2.j2` using Jinja2).
- The database records the `prompt_version`, `model_name`, and `provider` used for every successful generation, enabling A/B testing of prompt effectiveness and rollback capabilities.
